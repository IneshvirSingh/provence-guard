## 1. Mission

Build a **provenance-tracking policy layer for tool-using LLM agents** that blocks indirect prompt injection by design, prove it on a public benchmark, and ship it as a deployed, secure, observable production service.

1. **Research core:** a planner / quarantined-extractor agent (CaMeL-inspired, much smaller) where every value carries labels saying where it came from, and a deterministic policy engine checks those labels before any side-effecting tool call.

**60-second demo target:** the same malicious email/bill, side by side. The undefended agent wires money to the attacker; Provenance Guard blocks the call and shows *why*: "recipient came from `read_file(bill.txt)` (untrusted), policy `send_money.recipient ∈ {user, contacts}`".

## 5. Core design spec

### 5.1 Provenance model
- `Source`: `USER`, `SYSTEM`, or `TOOL(name, trusted: bool)`.
- `Labeled[T]`: an immutable value plus `sources: frozenset[Source]`. Any operation that derives a value takes the **union** of its inputs' sources. No operation may drop sources.
- **Trust config** (`policies/trust.yaml`): for each tool output, trusted or untrusted, justified in `docs/THREAT_MODEL.md`. Defaults: content written by third parties (email bodies, file contents, transaction subjects/memos, retrieved documents, web pages) is **untrusted**. The user's own query is `USER`.

### 5.2 Planner (privileged LLM)
- Sees **only** the user's request and tool schemas. Never raw tool outputs.
- Emits a `Plan` validated by Pydantic. v1 steps: `CallTool(name, args)`, where each arg is a literal or a ref; `Extract(from_ref, schema, instruction)`; bounded `ForEach(ref, max_items, steps)`; `Respond(template_with_refs)`.
- Document the limits of a linear plan (no data-dependent branching in v1) in an ADR, and measure what it costs in utility.

### 5.3 Quarantined extractor (unprivileged LLM)
- Receives untrusted text plus a target schema (types, enums, regexes such as IBAN format). Returns structured output only. **Has no tools.**
- Outputs inherit the sources of their inputs. Schema-invalid output is retried once, then fails closed.

### 5.4 Policy engine
- Pure, deterministic functions per side-effecting tool, e.g. `send_money.recipient` must have sources ⊆ {USER, TOOL(contacts, trusted)}; otherwise CONFIRM. Policies are versioned files with a schema, loaded per tenant.
- Decisions: `ALLOW | DENY | CONFIRM`, each with a machine-readable reason (which arg, which sources, which rule). Every decision is logged.
- Property tests: a value derived from an untrusted source can never be auto-allowed into a guarded argument, however it is composed.

### 5.5 Confirmation
- Interface with three implementations:
  - **strict** (CONFIRM → deny): the benchmark's lower bound on utility.
  - **permissive** (CONFIRM → approve): the benchmark's upper bound on attack success, i.e. a careless user.
  - **interactive** (LangGraph interrupt + HTTP approval): the product.
- Report **both** benchmark bounds and the confirmation rate. Never fake an "oracle" approver that peeks at ground truth.

### 5.6 Graph
`plan → validate_plan → execute_step (loop) → policy_check → [interrupt: confirm] → respond`, with OpenTelemetry spans and Langfuse traces on every node.

### 5.7 AgentDojo integration
Implement the defense as an AgentDojo pipeline / defense element, using whatever API the installed version exposes (verify it). Results are written as JSON with git SHA, package versions, model, date, suite, attack, defense and seed.

### 5.8 Fallback (scope-cut) design
If the planner design destroys utility, implement **argument-provenance matching** on a standard tool-calling loop: tag all tool outputs untrusted and block or confirm guarded arguments whose values appear in untrusted outputs. Document it as weaker and keep both results.
